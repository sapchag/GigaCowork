# Сценарии распределения, вопросы заказчику, алгоритм и допущения

## 1. Вопросы заказчику и участникам процесса

Задание требует найти не менее 5 мест, где правило неоднозначно или не описано,
и сформулировать по ним вопросы. Для каждого указаны: кому адресован, зачем, и
какое допущение принято до ответа.

### Вопрос 1. «Один поставщик в пачке — один логист» vs «предпочтительный логист по истории»
**Кому:** руководитель логистики.
**Почему важно:** правило «один поставщик — один логист» может конфликтовать с
правилом «предпочтительный логист по истории» и с «наименее загруженный». Если у
поставщика исторически несколько логистов, а в пачке новый поставщик — как выбирать.
**Допущение (до ответа):** в рамках одной пачки все новые заказы одного поставщика
получают одного и того же логиста — того, кого правила выбора назначили для первого
заказа поставщика в пачке. История и загрузка пересчитываются по всему реестру Cloud
(не только по пачке).

### Вопрос 2. Что считается заказом «в работе» и когда заказ перестаёт влиять на загрузку
**Кому:** руководитель логистики.
**Почему важно:** загрузка логиста считается по заказам «в работе». Неясно, как
трактовать статусы «confirm», «завершён», «закрыт» и как учитывать заказы с пустым
статусом.
**Допущение:** загрузка считается только по строкам со статусом «в работе» (как указано
в задании). Строки со статусом «confirm» и пустым статусом в загрузку не входят. Если
у логиста в реестре совсем нет строк — его загрузка 0.

### Вопрос 3. Как сопоставлять короткие имена из Cloud и ФИО из 1С (коллизии)
**Кому:** сотрудник распределения.
**Почему важно:** короткие имена (например «Иванов И.») могут совпадать у разных
сотрудников или не совпадать по склонению/регистру. Также непонятно, что делать с
именами, которые не удаётся сопоставить.
**Допущение:** сопоставление идёт по совпадению фамилии (без учёта регистра/пунктуации)
и первой буквы имени. При неоднозначности (несколько сотрудников под одним коротким
именем) используется табельный номер; если и он не помогает — сотрудник помечается
как «требует внимания» и ручной проверки.

### Вопрос 4. Номер заказа и формат комментария ФУЛ
**Кому:** сотрудник распределения.
**Почему важно:** номер заказа агент извлекает из комментария ФУЛ вида
«Номер: S0001234 от ДД.ММ.ГГГГ». Формат может отличаться (без «от», другой разделитель,
номер в другом месте). Нужно понять, насколько форма может варьироваться.
**Допущение:** агент ищет номер заказа по регулярному выражению «Номер[:.]? <код>», а
как запасной вариант — по первым строкам комментария. Если номер найти не удалось —
ФУЛ помечается «Требует внимания» (не создаётся строка, значение не выдумывается).

### Вопрос 5. Гонконг и «страна отправления» — как относится к ВЭД
**Кому:** руководитель логистики.
**Почему важно:** в задании сказано «не air + страна отправления Китай (включая
Гонконг) → ВЭД». Неясно, как трактовать написание «Гонконг» / «Hong Kong» / «Китай,
Гонконг» и какое покрытие стран считать «Китаем».
**Допущение:** страна «Китай», «Гонконг», «Hong Kong» (в любом регистре) и фразу,
содержащую «гонконг»/«hong», считаем страной отправления Китай → ВЭД для не-air способов.

### Вопрос 6. Возможные пропуски: как трактовать и какую дату считать «последней записью»
**Кому:** сотрудник распределения, логисты.
**Почему важно:** «возможный пропуск» — ФУЛ, которого нет в Cloud, хотя он пришёл
раньше последней записи Cloud. Не ясно, сравнивать ли с датой создания строки Cloud
или с датой получения УЛ в Cloud, и входит ли в сравнение закрытый/неактуальный ФУЛ.
**Допущение:** последняя запись Cloud определяется по максимуму поля «Дата получения УЛ»
во всех строках реестра. ФУЛ считаем «возможным пропуском», если его заказа нет в Cloud
(уникальный ключ) и дата ФУЛ раньше последней записи Cloud. Такой ФУЛ всё равно
распределяется как новый, но дополнительно выводится в лист «Возможные пропуски».

### Вопрос 7. Повторная отправка vs дубль внутри пачки
**Кому:** сотрудник распределения.
**Почему важно:** «повторная отправка» — когда заказ уже есть в Cloud; «дубль внутри
пачки» — когда тот же заказ/ФУЛ уже встречался в этой пачке. Нужно уточнить, считать
ли дублем одинаковый номер заказа или номер ФУЛ, и как приоритизировать, если оба условия.
**Допущение:** сначала проверяем номер ФУЛ (уникален), затем заказ в Cloud, затем заказ
в пачке. Повтор по номеру ФУЛ всегда трактуется как дубль в пачке, повтор по заказу
при наличии в Cloud — как «повторная отправка» с комментарием «Повторная отправка
ФУЛа, [дата]».

### Вопрос 8. Пустой логист и не полностью заполненные ФУЛ
**Кому:** сотрудник распределения.
**Почему важно:** непонятно, блокировать ли всю строку при отсутствии группы/логиста
или оставлять записи с пустыми полями и пометкой.
**Допущение:** при неопределённости группа/логист не заполняются, ФУЛ помечается
«Требует внимания» с причиной. Агент никогда не подставляет правдоподобных значений.

## 2. Алгоритм распределения

### Псевдокод

```
ВХОД: ful[] (ФУЛ из 1С), cloud[] (реестр Cloud), staff[] (сотрудники).

1. Для каждого ФУЛ: извлечь номер заказа из комментария (regex «Номер: X»).
   Ключ заказа = нормализованный номер (буквы/цифры, нижний регистр).
2. Построить индекс Cloud по ключу заказа.
3. Построить короткое имя логиста Cloud -> сотрудник 1С (фамилия + первая буква имени).
4. Сортировать ФУЛ по дате (возрастание), чтобы повторы обрабатывались
   предсказуемо.
5. Для каждого ФУЛ:
     а) если номер заказа не извлечён -> «Требует внимания» (нет номера заказа).
     б) если номер ФУЛ уже встречался в пачке -> ДУБЛЬ В ПАЧКЕ.
     в) если заказ есть в Cloud -> ПОВТОРНАЯ ОТПРАВКА
        (комментарий «Повторная отправка ФУЛа, [дата]»).
     г) если заказ уже обработан в этой пачке -> ДУБЛЬ В ПАЧКЕ.
     д) определить группу:
          delivery == air                  -> авиаперевозки
          delivery != air и страна = Китай/Гонконг -> ВЭД
          delivery != air и страна = не Китай    -> мультимодальные
          (нет способа/страны -> группа не определена -> «Требует внимания»)
     е) выбрать логиста в группе:
          доступные сотрудники = роль=группа, состояние=Работает,
                                не ассистент, не руководитель.
          если группа пуста -> логист не определён -> «Требует внимания».
          история: среди доступных выбрать того, кто чаще всех вёл поставщика в Cloud.
          если истории нет, или предпочтительный недоступен ->
             выбрать наименее загруженного (мин. заказов «в работе») в группе.
          (ничья по загрузке -> по алфавиту короткого имени — детерминизм.)
     ж) один поставщик в пачке: если этот поставщик уже назначен логисту в пачке,
        использовать его же.
     з) создать строку Cloud: 12 колонок по форме реестра, статус «в работе»,
        дата получения УЛ = дата ФУЛ, cut-off как есть.
6. Возможные пропуски: заказы, которых нет в Cloud, но дата ФУЛ < последней записи Cloud.
7. Собрать результат: новые строки Cloud, повторные отправки, пропуски,
   «Требует внимания», журнал решений по каждому ФУЛ.
ВЫХОД: Excel-файл (5 листов).
```

### Сложные случаи

| Случай | Ожидаемое поведение |
|--------|---------------------|
| Повторная отправка ФУЛ (заказ уже в Cloud) | НЕ создавать строку; добавить в «Повторные отправки» с комментарием «Повторная отправка ФУЛа, [дата]». |
| Новый поставщик (нет истории) | Выбрать наименее загруженного в группе. |
| Предпочтительный логист в отпуске | Исключить его; выбрать наименее загруженного из оставшихся в группе. |
| Предпочтительный логист уволен | Исключить его; выбрать наименее загруженного из оставшихся в группе. |
| Все сотрудники группы недоступны | Оставить логиста пустым, НЕ передавать в другую группу, пометить «Требует внимания». |
| Нет номера заказа | Не создавать строку, пометить «Требует внимания». |
| Нет способа доставки | Группа не определена, пометить «Требует внимания». |
| Нет страны отправления (не-air) | Группа не определена, пометить «Требует внимания». |
| Один поставщик в пачке | Все его заказы назначать одному логисту. |
| Варианты написания поставщика | Нормализовать (буквы/цифры, нижний регистр): «Гуанчжоу Текстиль Лтд», «гуанчжоу текстиль», «Гуанчжоу-Текстиль» — одна сущность. |
| ФУЛ раньше последней записи Cloud | Распределить как новый ДОПОЛНИТЕЛЬНО показать в «Возможных пропусках». |

## 3. Принятые допущения (сводка)

1. Загрузка логиста = число строк реестра Cloud со статусом «в работе», содержащих
   это короткое имя (сопоставленное с ФИО).
2. Предпочтительный логист = сотрудник группы, чаще всех вёдший поставщика в Cloud
   (по всему реестру, не по пачке).
3. Наименее загруженный = минимальная загрузка в группе; при ничьей — по алфавиту
   короткого имени (детерминированность).
4. «Один поставщик — один логист» реализован в рамках одной пачки: первый заказ
   поставщика назначает логиста, остальные заказы того же поставщика в пачке получают
   того же.
5. Повтор в пачке определяется сначала по номеру ФУЛ, затем по заказу.
6. Страна «Китай, включая Гонконг» трактуется по вхождению ключевых слов
   «кита», «гонконг», «hong» (в любом регистре).
7. Даты сравниваются с точностью до дня; при невозможности распознать дату ФУЛ
   принимаем его минимально возможной датой и не выводим в «возможные пропуски».
8. Агент не гадает: если данных не хватает — «не определено» + причина в журнале.
9. Колонки ищутся по заголовкам (нормализованным) независимо от порядка и наличия
   дополнительных колонок.
10. Новые строки Cloud заполняются по строгой форме: 12 колонок в порядке реестра.
